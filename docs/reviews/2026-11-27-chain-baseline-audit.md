## 会影响结果的差异

1. **当前启动入口未执行 v4。** src/audio3a/scripts/run_g7_wpe_dpdfnet2_nvidia.sh 启动 p2p_dut_node，NVIDIA 读线程之后只调用 apply_nvidia_post_leveling。未调用 scripts/v4_post.sh，也未调用 v4_live_pcm。README 的链路图包含 v4，需明确它是待接入后级还是另外生成的试听版本。scripts/v4_post.sh 包含 dynaudnorm/loudnorm，不能直接当作零等待实时后级。

2. **“raw”采集位于校准增益之后。** p2p_dut_node.c 在线循环将放大、限幅后的值写回 mic_raw，之后才 fwrite。源码足以证明该录音入口不是 ADC 原始值；但不能据此断言现有六份文件的全部采集历史。要补采集来源和是否校准的元数据；后续采集应在更改原始缓冲之前保存。现有文件保持原样。

3. **评测复现尚未闭环。** t32_correct.py、role_split.py 依赖已经删除的 out/ 模型/实现；order_test.py 依赖 /tmp/nveval 和另一台机器的 /mnt/data 路径。仓库的 Audio3A 源码也未带入独立构建入口及依赖说明。复查时已出现仓库内 nvidia_runner.py、相对模型路径与 NVIDIA_T32_ONNX 配置，NVIDIA 这部分正在修正；order_test 的录音路径及完整 Audio3A 构建仍需处理。

4. **DPDF 离线复现仍需校准。** role_split.py 使用 FFT=512，而板端为 510；其 run_t32 只在每个 stride 写 128 样本，其余留零，不能用于评价实际 T32。order_test.py 的 DPDF 采用 sqrt-Hann 和全零状态，板端采用 Vorbis 窗和模型元数据初始状态；也未补偿启动延迟/尾部。复查时 role_split 已改为共用 T32 实现，t32_correct 也已修复 tuple 解包；这些修订须完成数值验证。DPDF 的窗、初始状态、延迟与 EOF 问题仍在。

5. **两套实时参数不同。** 新 Audio3A 桥接 T32 使用 history=48 ms、overlap=48 ms、stride=152 ms；旧 scripts/board 入口使用 overlap=72 ms、stride=128 ms。本轮 002/DUT 单麦实验属于后者。速度、排队和音质都要标注参数，不能合并排名。

6. **核号不能照搬。** 当前板卡 sysfs 显示 CPU 1–4 为 A76，0、5–7 为 A55；新启动脚本固定 taskset 4-7，只包含一个 A76。应按实际 core topology 配置并记录 CPU 亲和性，重新测整链负载，避免把 CPU 调度影响误判为 NPU 性能。

7. **“反序不可实时”并非结构上的限制。** 现有实现可以在 NVIDIA 输出线程串接 CPU 降噪或另设输出工作线程，无需让采集线程同步等待。是否满足预算要测。原说明中“异步所以不可行”应改成“当前入口尚未实现并验收”。

8. **固定掩码也要先对齐。** DPDF 启动、10/16 ms FIFO 和 NVIDIA 窗口会产生延迟，stage_audit 直接沿用原索引并不等于声学时间对齐。要先处理延迟和尾部，避免把错位弱字判成噪声或尾音。语音/停顿落差属于代理指标，不是有干净参考的真实 SNR 或 DRR。
